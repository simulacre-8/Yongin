# 용인시 데모 현재 DB·화면 갭 보고

**기준일:** 2026-09-06

**검증 환경:** 호스팅형 Supabase + React/Netlify

**목적:** 디자인 개편과 별개로, 현재 실제 DB에서 동작하는 범위와 시연 전 추가 연결이 필요한 범위를 구분한다.

## 1. 결론

Supabase 자체는 정상이다. 공개 브라우저 키 기준으로 필수 테이블 19개와 비공개 증빙 버킷을 조회했고, 대상 CRUD·감사로그·Storage 업로드/다운로드/삭제가 모두 통과했다. ADOMS 규칙 조회와 적용범위 판정 스냅숏 저장도 실제 원격 DB에서 통과했다.

다만 **화면 전체가 원격 DB로 연결된 상태는 아니다.** 현재 실제 원격 데이터가 화면에 연결된 영역은 적용범위 판정, 관계 법령 목록, 관리대상 목록, 시설별 법 의무사항 조회다. 법 의무사항은 시설 151개와 대상–의무 매핑 2,929건을 직접 조회한다. 이행현황·법 의무사항 이행시기 저장·실적증빙·이행점검·총괄표는 화면과 로컬 시연 흐름은 있으나 업무값을 브라우저 localStorage 또는 컴포넌트 메모리에 저장한다. 따라서 같은 브라우저 안에서는 바뀐 값이 보이지만, 다른 PC·다른 사용자·새 세션까지 공유되는 업무기록이라고 설명하면 안 된다.

## 2. 실제 원격 DB 상태

아래 참조 데이터 건수는 관리자 전체 행 기준이다. 브라우저 공개키에는 RLS를 통과한 승인 데이터만 노출되므로 규칙·연결의 화면 조회 건수는 전체 건수보다 작다.

| 데이터 영역                                    | 원격 건수 | 현재 화면 사용             | 상태                               |
| ---------------------------------------------- | --------: | -------------------------- | ---------------------------------- |
| 법령 `ref_law`                                 |       115 | `/laws`, 적용판정 근거     | 정상                               |
| 조문 `ref_unit`                                |       393 | 적용판정 근거              | 정상                               |
| 판정 규칙 `ref_rule`                           |       132 | `/`, `/applicability`      | 정상                               |
| 의무 마스터 `ref_obligation`                   |       310 | 적용판정·시설별 의무 상세  | 정상                               |
| 규칙-의무 연결 `ref_rule_obligation`           |       138 | 적용판정 규칙 조합         | 정상                               |
| 관리대상 참조 `ref_managed_target`             |       153 | `/targets`, `/obligations` | 정상: FMS 150 + 시연 3             |
| 대상-의무 연결 `ref_managed_target_obligation` |     2,929 | 두 화면의 의무 수·상세     | 정상: 고유 의무 84                 |
| 실제 업무 대상 `target`                        |         1 | 적용판정 저장 대상         | 정상                               |
| 적용판정 결과 `target_applicability`           |         8 | `/`, `/applicability` 저장 | 정상                               |
| 대상별 의무 `target_obligation`                |        10 | 화면 미연결                | DB 존재                            |
| 이행기록 `compliance_record`                   |        10 | 화면 미연결                | DB 존재                            |
| 증빙 메타데이터 `evidence`                     |         0 | 화면 미연결                | 테이블·Storage 존재, 업무 증빙 0건 |
| 점검회차 `inspection_run`                      |         1 | 화면 미연결                | DB 존재                            |
| 점검범위 `inspection_scope`                    |        10 | 화면 미연결                | DB 존재                            |
| 점검결과 `inspection_result`                   |        10 | 화면 미연결                | DB 존재                            |
| 감사로그 `audit_event`                         |      200+ | 운영 검증                  | 정상, 스모크 테스트 때 증가        |

용인경전철은 FMS 시설물이 아니라 `공중교통수단`으로 별도 분류되어 있으며, 근거 경로는 도시철도법 제2조제2호·중대재해처벌법 제2조제5호·시행령 별표 2·3으로 저장돼 있다.

## 3. 화면별 동작 상태

| 화면               | 현재 보이는 내용                             | 원격 DB 연결                      | 실제 저장                                          |
| ------------------ | -------------------------------------------- | --------------------------------- | -------------------------------------------------- |
| 적용범위 판정      | 인원·면적 변경, L1→L2→L3 후보, 규칙 근거     | ADOMS 법령·조문·규칙·의무 조회    | `target_applicability` 원격 저장                   |
| 이행현황           | 대상·시기도래·기한초과·이행률·알림·확보의무  | 없음                              | localStorage 상태를 집계                           |
| 관리대상 현황      | FMS 150건, 경전철, 도급·용역 시연 대상       | `v_managed_target_summary` 조회   | 목록은 원격, 상세·계약 입력은 메모리               |
| 관계 법령 관리     | 법령 115건 검색·필터                         | `ref_law` 조회                    | 읽기 전용                                          |
| 법 의무사항        | 시설 151개, 대상별 의무·관계법령·이행시기 표 | 시설·의무 매핑과 의무 마스터 조회 | 이행시기는 대상별 localStorage 저장                |
| 의무이행(실적증빙) | 의무별 입력표, 파일 선택, 증빙 예시          | 없음                              | 요약값은 localStorage, 파일은 현재 브라우저 메모리 |
| 이행점검 및 조치   | 취합 대상 선택, 상태·점검내용 편집           | 없음                              | localStorage                                       |
| 점검 총괄표        | O·△·X·- 및 이행률                            | 없음                              | 점검 localStorage를 화면에서 집계                  |

상단 연결 배지는 Supabase의 **기준정보 접근 상태**를 뜻한다. 이행·증빙·점검 전체가 원격 저장된다는 의미로 사용하지 않는다.

## 4. DB는 있으나 화면 연결이 없는 영역

`target_obligation`, `compliance_record`, `inspection_run`, `inspection_scope`, `inspection_result`는 이미 존재하고 시드도 있다. 시설별 법 의무사항의 읽기 연결은 완료됐다. 남은 영역은 새 DB를 설계하기보다 다음의 업무기록 어댑터를 연결하는 것이 우선이다.

| 우선순위 | 연결 작업                                                                       | 기대 효과                               |
| -------- | ------------------------------------------------------------------------------- | --------------------------------------- |
| 완료     | `ref_managed_target_obligation`과 `ref_obligation` 화면 조인                    | 151개 대상의 실제 의무가 화면에 표시    |
| P0       | 시설 참조 대상을 업무 `target`으로 승격하고 `target_obligation.due_*` 조회·저장 | 이행시기 원격 영속                      |
| P0       | 실적증빙의 `compliance_record` 저장 및 `evidence-private` 업로드                | 실제 파일·조치일·비고가 남음            |
| P0       | 점검의 `inspection_run/scope/result` 조회·저장                                  | 취합→점검→총괄표 폐쇄 루프 완성         |
| P0       | 이행현황을 `v_dashboard_summary` 또는 전용 조회로 연결                          | 다른 화면의 저장 결과가 대시보드에 반영 |
| P1       | 관리대상 상세 입력을 대상별 업무 레코드로 저장                                  | 주소·업종·인원·담당자 보존              |

## 5. 현재 DB에 없는 영역

다음은 테이블 또는 API 계약이 아직 없어서, 실제 저장을 원하면 새로 설계해야 한다. 화요일 시연에서는 더미 데이터를 화면에 보이게 할 수 있지만, 실제 업무기록이라고 설명해서는 안 된다.

| 영역                     | 부족한 데이터 또는 API                                      | 화요일 권장 처리                                |
| ------------------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| 도급·용역·위탁 계약 상세 | 계약, 계약기간, 업체, 위험장소, 준수상태, 계약 첨부 테이블  | 시나리오 고정 더미 + `시연값` 표시              |
| 관리대상 상세 이력       | 기준일별 주소·업종·8종 인원·담당자·관리감독자·첨부          | 용인시청 기준 더미, 저장은 후순위               |
| 증빙 가변 상세행         | 인력·예산·점검·계획·법정교육별 행 스키마                    | `detail_json` 또는 유형별 상세 테이블 컨펌 필요 |
| 알림·조치지시            | 수신자·발신자·읽음·조치기한·처리이력                        | 대시보드 고정 알림만 표시                       |
| 결재·확정                | 결재선·결재자·승인시각·잠금·반려이력                        | 버튼 비활성 유지                                |
| Excel 내보내기           | 생성 API·내보내기 이력                                      | 버튼 비활성 또는 화면 CSV만 제공                |
| 직원·조직 검색           | 인사·조직 마스터와 검색 API                                 | 검색 모달을 만들지 않고 이름 직접입력           |
| Bitemporal 이력          | 발생시각(valid time)과 입력·판정시각(transaction time) 분리 | 지금은 스냅숏 저장, 운영형 전환 때 추가         |

## 6. 현재 8개 대표 화면에서 빠진 원본 화면 기능

현재 앱은 102개 원본 화면을 모두 개별 라우트로 복제한 제품이 아니라 8개 대표 시연 화면으로 정규화한 데모다. 다음 기능은 별도 화면 또는 모달로 아직 구현하지 않았다.

- 로그인·비밀번호·사용자 관리와 실제 역할 권한 설정
- 관계법령 상세 편집·신규 등록 및 법령 검색 팝업
- 예방계획 불러오기, 직원 검색, 조직 검색
- 도급·용역·위탁 계약 저장과 계약 첨부 원본 관리
- 메시지 보내기·조치지시·수신/발신 이력
- 결재·반려·확정 후 잠금과 재점검 이력
- 실제 증빙파일 미리보기·버전 다운로드
- Excel 내보내기와 보고서 생성
- 통계 상세, 사고 사례, 재발방지 사례의 독립 화면

## 7. 클라이언트 확인이 필요한 결정

첫째, 화요일 필수 성공 흐름을 **적용판정 → 대상별 의무 → 이행시기 → 증빙 → 점검 → 총괄표 → 이행현황 반영**으로 확정할지 확인이 필요하다. 이 흐름이면 신규 화면보다 기존 8개 화면의 원격 데이터 연결을 우선한다.

둘째, 도급·용역·위탁 계약 상세와 관리대상 인원·담당자 이력은 더미 표시만으로 충분한지, 실제 저장까지 요구하는지 확인이 필요하다. 실제 저장을 요구하면 별도 테이블 설계 범위가 추가된다.

셋째, 증빙 상세를 범용 `detail_json`으로 빠르게 저장할지, 인력·예산·점검·교육별 정규 테이블로 만들지 확인이 필요하다. 화요일 데모에는 전자가 빠르지만 운영형 전환에는 후자가 적합하다.

넷째, 102개 원본 화면 중 이번 시연에서 반드시 독립 화면으로 보여야 하는 화면 번호가 있는지 확인이 필요하다. 지정이 없으면 현재 8개 대표 라우트 안에서 상태 전환으로 재현한다.

## 8. 권장 실행 순서

디자인은 초기 용인시 브랜드 톤으로 통일하되, 화면의 필드와 메뉴 깊이는 현재 시연자 위치 기억을 보존한다. 이후 P0 데이터 연결을 순서대로 완료한다. 새 그래프 DB나 외부 Graph API는 이번 시연에 필요하지 않다. 현재 Supabase 투영 데이터와 원본 식별자를 유지하면 추후 GraphDB로 복귀할 수 있다.
