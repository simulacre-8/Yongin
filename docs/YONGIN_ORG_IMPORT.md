# 용인특례시 공식 조직도 DB 구축

**원천 기준일:** 2026-09-06  
**적재 대상:** Supabase 프로젝트 `gxpfnszbwvfyogwshvas`

## 구축 결과

용인특례시 공식 조직도 세 화면과 공개 부서 상세 조회를 파싱해 별도 참조 계층으로 구축했다. 기존 시연용 `org`·`profile` 테이블은 수정하지 않았으며, 공식 조직 스냅숏은 `ref_yongin_org_snapshot`, 조직 단위는 `ref_yongin_org_unit`, 현재 계층 조회는 `v_yongin_org_tree`에서 제공한다.[1][2][3]

공식 조직도에 표시된 **시청 2실·13국·66과, 의회사무국 2담당관, 직속기관 4기관·9과, 사업소 5사업소·14과, 3개 구청·38과·39읍면동**은 파싱 결과와 일치한다. 팀 이름은 조직도 본문에 직접 나열되지 않아 공개 부서 상세 표의 고유한 `…팀장` 직위에서 파생했다. `부팀장`은 팀 이름이 아니므로 명시적으로 제외했으며, 개인 이름·개인 전화번호·이메일은 적재하지 않았다.

## 팀 수 해석

공식 조직도 상단의 팀 합계와 공개 담당자 목록에서 현재 확인되는 팀장 직위 수는 동일한 스냅숏 의미를 보장하지 않는다. 휴직·공석·겸임·TF, 도서관의 `…도서관장`처럼 팀장이 아닌 직위명, 읍·면·동 팀의 별도 합산 범위 때문에 차이가 생길 수 있다. 따라서 공식 합계는 스냅숏 `summary.expected_official_counts`에 보존하고, DB의 `TEAM` 행은 실제 공개 화면에서 확인된 고유 팀명만 저장했다. 누락 수를 맞추기 위한 가상 팀은 생성하지 않았다.

| 구역        | 공식 팀 합계 | 공개 `…팀장` 기반 팀 | 비고                                            |
| ----------- | -----------: | -------------------: | ----------------------------------------------- |
| 시청        |          276 |                  277 | 공개 담당자 목록 현재값                         |
| 의회사무국  |            9 |                   10 | 공개 담당자 목록 현재값                         |

| 3개 구청 과 |          166 |                  119 | 읍·면·동 하위 팀 97개는 별도                    |

## 데이터 모델

| 리소스                    | 목적                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| `ref_yongin_org_snapshot` | 원천 URL, 수집시각, 공식 수량, 파싱 수량 보존                                             |
| `ref_yongin_org_unit`     | 안정 키, 부모 키, 공식 부서코드, 이름, 유형, 전체 경로, 위치, 대표 팀 전화, 원천 URL 보존 |
| `v_yongin_org_tree`       | 부모명과 활성 자식 수를 포함한 현재 조직 계층 읽기 모델                                   |

`org_key`는 전체 계층 경로를 기반으로 만든 안정 키다. 공식 사이트가 기관과 하위 조직에 같은 부서코드를 재사용하는 사례가 있어 `source_code`만 기본키로 사용하지 않는다. 원천 조직 개편 시 기존 행을 덮어쓰기보다 최신 파싱 결과에 없는 행을 `is_active=false`로 전환한다.

## 재현 절차

```bash
python3 scripts/build-yongin-org-seed.py --workers 8 --strict
```

이 명령은 다음 산출물을 다시 생성한다.

| 산출물                               | 용도                         |
| ------------------------------------ | ---------------------------- |
| `data/yongin_org_units_20260906.csv` | 검수 가능한 조직 단위 CSV    |
| `supabase/seed_yongin_org.sql`       | 멱등 Supabase 적재 SQL       |
| `docs/YONGIN_ORG_IMPORT_REPORT.json` | 수량·원천·개인정보 범위 보고 |

DB에는 `010_yongin_org_catalog.sql`, `011_yongin_org_tree_view.sql`, `seed_yongin_org.sql` 순서로 적용한다. 공개 publishable key 기준 검증은 다음 명령으로 수행한다.

```bash
pnpm check:supabase
pnpm smoke:org
```

`smoke:org`는 활성 792건, 공식 구조 수량, `중대재해예방팀`, `도시철도과`, 공식 부서코드, 계층 자식 수, `부팀` 오인식 0건을 검증한다.

## 현재 연계 범위

공식 조직 DB에는 `안전정책관 / 중대재해예방팀`, `재난대응담당관 / 재난대응팀`, `교통정책국 / 도시철도과 / 경전철관리팀`, `상수도사업소 / 수도시설과 / 수도시설팀` 등이 실제 계층과 함께 들어 있다. 다만 시설·의무 workflow의 담당 조직 외래키는 아직 연결하지 않았다. 다음 단계에서는 클라이언트가 담당부서 매핑 기준을 확인한 뒤 `target_ref` 또는 `target_obligation_id`에 `org_key`를 연결해야 하며, 이를 임의 배정하지 않는다.
